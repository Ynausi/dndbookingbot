# D&D Booking Bot

Telegram-бот для бронирования игровых сессий по Dungeons & Dragons.

Бот позволяет игрокам просматривать доступных мастеров, выбирать свободные даты и временные слоты, а также создавать бронь прямо через Telegram.

В качестве основного источника данных используются Google Sheets. Для уменьшения задержек при обращении к Google Sheets API часто используемые данные кэшируются на стороне приложения.

## Возможности

* просмотр доступных мастеров
* просмотр карточки мастера
* бронирование D&D-сессий
* выбор бронирования по:

  * мастеру
  * дате
  * временному слоту
* поддержка one-shot и campaign форматов
* просмотр свободных дат
* просмотр свободных временных слотов
* фильтрация мастеров по доступности
* регистрация мастера через Telegram
* управление фотографией мастера
* административные функции
* интеграция с Google Sheets
* кэширование данных
* хранение временного состояния процесса бронирования

## Архитектура

Приложение разделено на несколько логических частей:

```text
Telegram
   |
   v
Update Dispatcher
   |
   +-------------------+
   |                   |
   v                   v
Text Handlers      Callback Handlers
   |                   |
   +---------+---------+
             |
             v
          Services
             |
      +------+------+
      |             |
      v             v
    Cache      Google Sheets API
```

Основные пакеты приложения:

```text
ru.ynausi.dndbookingbot
├── admin
├── booking
├── bot
│   ├── callback
│   ├── command
│   ├── update
│   └── view
├── configuration
├── master
├── schedule
└── session
```

### Bot layer

Отвечает за взаимодействие с Telegram.

Этот слой:

* принимает Telegram Updates
* обрабатывает текстовые сообщения
* обрабатывает callback-запросы
* формирует клавиатуры
* формирует сообщения
* передает выполнение бизнес-логики сервисам

### Booking layer

Отвечает за временное состояние процесса бронирования.

Пример процесса:

```text
Выбор мастера
      |
      v
Выбор даты
      |
      v
Выбор временного слота
      |
      v
Подтверждение брони
```

Состояние бронирования пользователя временно хранится в памяти приложения.

### Schedule layer

Отвечает за расписание мастеров.

Основные задачи:

* получение расписания из Google Sheets
* поиск свободных дат
* поиск свободных временных слотов
* поиск свободных мастеров
* обновление расписания после бронирования

Чтобы не обращаться к Google Sheets API при каждом запросе, расписание кэшируется внутри приложения.

### Master layer

Содержит данные и бизнес-логику, связанную с мастерами.

Например:

* получение списка активных мастеров
* поиск мастера
* получение профиля мастера
* сохранение Telegram ID мастера
* сохранение Chat ID мастера
* обновление фотографии мастера

### Google Sheets

Google Sheets используется одновременно как источник данных и как простая административная панель.

Это позволяет организаторам изменять:

* список мастеров
* расписание
* доступность
* служебные данные

без необходимости создавать отдельную веб-панель администратора.

Для доступа к Google Sheets используется Google Service Account.

## Кэширование

Обращения к Google Sheets API создают дополнительную сетевую задержку.

Для уменьшения времени ответа приложение кэширует часто используемые данные:

* информацию о мастерах
* расписание
* информацию об администраторах

После успешного изменения расписания соответствующие данные в кэше также обновляются.

Это уменьшает количество запросов к Google Sheets API и ускоряет работу Telegram-бота.

## Конфигурация

Приложение использует следующие переменные окружения:

```text
BOT_TOKEN
GOOGLE_SPREADSHEET_ID
```

Пример конфигурации:

```yaml
telegram:
  bot:
    token: ${BOT_TOKEN}

google:
  sheets:
    spreadsheet-id: ${GOOGLE_SPREADSHEET_ID}
    credentials-path: classpath:google/service-account.json
```

## Google Service Account

Для работы с Google Sheets необходимо создать Service Account в Google Cloud и скачать JSON-файл с credentials.

Файл необходимо разместить по пути:

```text
src/main/resources/google/service-account.json
```

Файл с credentials исключен из Git и не должен попадать в репозиторий.

После этого необходимо предоставить Google Service Account доступ к нужной таблице Google Sheets.

## Запуск проекта

### Требования

Для запуска необходимы:

* Java 21+
* Maven
* Telegram Bot Token
* Google Service Account
* Google Spreadsheet с нужной структурой данных

Клонировать репозиторий:

```bash
git clone https://github.com/Ynausi/dndbookingbot.git
cd dndbookingbot
```

Установить переменные окружения.

Linux/macOS:

```bash
export BOT_TOKEN="your_telegram_bot_token"
export GOOGLE_SPREADSHEET_ID="your_google_spreadsheet_id"
```

Windows PowerShell:

```powershell
$env:BOT_TOKEN="your_telegram_bot_token"
$env:GOOGLE_SPREADSHEET_ID="your_google_spreadsheet_id"
```

Запустить приложение:

```bash
./mvnw spring-boot:run
```

Для Windows:

```powershell
mvnw.cmd spring-boot:run
```

## Сборка проекта

Собрать проект:

```bash
./mvnw clean package
```

Запустить тесты:

```bash
./mvnw test
```

## Пример процесса бронирования

Пример бронирования one-shot игры:

```text
Пользователь открывает бота
        |
        v
Выбирает One Shot
        |
        v
Выбирает мастера
        |
        v
Выбирает свободную дату
        |
        v
Выбирает временной слот
        |
        v
Подтверждает бронирование
        |
        v
```

## Текущие ограничения

Проект продолжает развиваться.

На данный момент есть следующие ограничения:

* booking-сессии хранятся в памяти приложения
* Google Sheets используется как основной persistence layer
* покрытие автоматическими тестами пока ограничено
* приложение в первую очередь рассчитано на запуск в одном экземпляре
* защита от конкурентного двойного бронирования требует дальнейшего улучшения

В дальнейшем планируется:

* увеличить покрытие unit- и integration-тестами
* добавить защиту от конкурентного double booking
* разделить крупные callback-handler'ы на более маленькие компоненты
* добавить время жизни для неактивных booking-сессий
* добавить Docker

## Почему Google Sheets

Google Sheets был выбран осознанно, потому что он одновременно выполняет роль удобного интерфейса для организаторов.

Мастера, расписание и доступность могут изменяться вручную без отдельной административной панели.

Основной недостаток такого подхода — задержки при обращении к внешнему API.

Для уменьшения количества запросов и ускорения работы используется локальное кэширование.
